# 컴파일러 연구 기록

`rg`의 목표는 특수 커널 없이도 일반 수학 코드가 컴파일만으로 빨라지는 것입니다. 이 페이지는 그 방법들을 어떻게 시험했고 무엇을 남겼는지 기록합니다. **통하지 않은 시도도 남겼습니다.** 다시 같은 길을 걷지 않기 위해서입니다.

"최적의 컴파일러"는 보장할 수 없습니다. 규칙에 없는 동치는 찾을 수 없고, 비용 모델은 근사이며, 뒤에서 보듯 실제 하드웨어는 모델을 벗어납니다. 그래서 목표를 측정 가능한 형태로 바꿨습니다. 대표 프로그램 모음으로 실측해, **이득이 입증된 것만 기본값으로 둡니다.**

## 모드

| `optimize=` | 내용 | 결정적 |
| --- | --- | --- |
| `"none"` | 죽은 코드 제거만 | O |
| `"standard"` | 폴딩, CSE, 대수 단순화, 전치 행렬곱, 재계산 | O |
| `"search-linear"` (기본값) | + 행렬곱 재결합·인수 묶기 | O |
| `"search-exact"` | `standard` + IEEE 754에서 엄밀한 규칙만 | O |
| `"search"` | + 원소 연산의 결합·교환·분배 | O |
| `"auto"` | `standard`와 `search-linear`를 실제로 돌려 빠른 쪽 선택 | X |

## 시도별 결론

| 시도 | 결과 | 결론 |
| --- | --- | --- |
| **Equality saturation** ([egg](https://arxiv.org/abs/2004.03082)), 행렬곱 규칙 | 행렬 체인 최적 순서를 동적 계획법 기준 1% 안으로 찾음. 큰 이득 | **채택** |
| 원소 연산 결합·교환·분배 (Horner 등) | 연산 수는 줄지만 시간은 거의 그대로이고, GPT 컴파일이 3배 느려짐 | 선택 사항으로 격리 |
| **공유를 보는 DAG 추출** | GPT에서 0.1% 미만 개선에 이차 시간. 층 32개 GPT 컴파일이 34ms에서 277초 | **삭제** |
| **추출 후 지역 탐색** | 위와 같음. 인위적인 테스트에서만 차이 | **삭제** |
| **실측 기반 선택** (`auto`, Ansor 계열) | 모델이 틀린 경우를 잡지만 계획이 실행마다 달라질 수 있음 | 선택 사항 |
| **사전 필터** | 행렬곱 연쇄가 없으면 탐색 생략. 층 32개 GPT 2.7초 → 38ms | **채택** |
| **채택 문턱** (추정 비용 10% 이상 감소) | 잡음 수준 재작성으로 반올림만 바꾸는 일을 막음 | **채택** |
| **검증 후 채택** | f64 동치 검사에 실패한 재작성은 버리고 표준 계획 사용 | **채택** |
| **중간값 재계산** | large GPT 메모리 12.66 GB → 5.01 GB, 스왑이 사라져 CPU 3배 향상 | **채택** |
| **GPU 스케줄 후보 비교** | 레벨 순서는 GPT 12% 이득, 다항식은 2배 손해. 추정치로 고름 | **채택** |
| Tiling, 동적 메모리 재배치 (MLIR 계열) | 시도하지 않음 | 미정 |

## 규칙의 안전 등급

| 등급 | 예 | 보장 |
| --- | --- | --- |
| 엄밀 | `-(-x) = x`, `a+b = b+a`, `(Aᵀ)ᵀ = A` | NaN과 무한대까지 같은 값 |
| 반올림 차이 | `(AB)C = A(BC)`, `AB+AC = A(B+C)` | 값은 반올림 차이만큼 다를 수 있음. 동치 검사로 확인 |
| 넣지 않음 | `sqrt(x)² = x`, `log(exp(x)) = x`, `x·0 = 0`, `x-x = 0` | 정의역이나 NaN·Inf 동작이 바뀜 |

`x·0 = 0`을 넣지 않는 이유는 진단 때문입니다. NaN을 지우면 원인을 찾을 증거가 사라집니다.

## 비용 모델

M4 Pro에서 잰 값으로 만든 근사입니다. CPU는 원소당·곱셈당 비용이 지배하고, GPU는 디스패치당 고정 비용이 큽니다. 다른 칩에서는 다시 재야 합니다. 모델은 후보를 제안할 뿐이며, 채택은 전체 그래프 비용 비교와 동치 검사를 거칩니다.

## 측정에서 배운 것

- **잘못된 측정이 가장 비싸다.** 준비 시간이 섞인 벤치마크가 없는 격차를 만들었고, 먼저 측정되는 쪽이 GPU 깨우기 비용을 떠안아 "2배 이득"이 나온 적도 있습니다. 같은 그래프끼리 시간이 다르면 먼저 측정을 의심해야 합니다.
- **연산 수는 시간이 아니다.** Horner 형태는 곱셈을 크게 줄이지만, 원소 연산은 메모리 대역폭에 막혀 있어 시간은 거의 그대로입니다.
- **직관은 자주 틀린다.** BLAS 전치 플래그에 숨은 비용이 있을 거라 봤지만 실측으로 기각됐습니다. 공유를 못 보는 추출이 치명적일 거라는 예상도 틀렸습니다.

## 알려진 미해결

- `repeated_transposes`는 `search-linear`에서 CPU가 약 0.83배로 느려집니다. 같은 크기의 행렬곱이 표준 계획에서는 호출당 111µs, 재작성 계획에서는 350µs입니다. BLAS 내부 동작으로 보이며, 원인을 확정하지 못했습니다. `auto`는 이 경우를 피합니다.
- 비용 모델은 메모리를 보지 않습니다. 재작성이 피크 메모리를 늘릴 수 있습니다.
- `scan` 본문에는 수식 탐색을 적용하지 않습니다.
- 작업 모음은 9개이고 M4 Pro 한 대뿐입니다. `search`가 실제 코드에서 값을 할 가능성은 열려 있습니다.

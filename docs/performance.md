# 성능

모든 수치는 Apple M4 Pro(16코어 GPU), f32, 2026-11-09 측정값입니다. 단위는 steps/s이고 높을수록 좋습니다. 프레임워크마다 새 프로세스에서 측정했습니다. 실행마다 약 ±15% 흔들리므로 그 안의 차이는 순위로 읽지 마세요.

CUDA와 NVIDIA GPU는 측정하지 않았습니다. `rg`가 지원하지 않기 때문이며, 그 환경에서는 PyTorch와 JAX가 압도적으로 빠릅니다.

## 문자 GPT 학습

`benches/gpt_compare.py`. 같은 구조, AdamW, 드롭아웃 없음. 앞의 세 열은 Apple GPU, 뒤의 네 열은 CPU입니다. 굵은 글씨는 행의 최고값입니다. 컴파일과 첫 버퍼 할당 같은 일회성 준비 시간은 프레임워크 모두 제외했습니다.

| 설정 | rg metal | MLX | torch MPS | rg cpu | torch | torch.compile | JAX jit |
| --- | --- | --- | --- | --- | --- | --- | --- |
| tiny (B=16, T=32, d=64, 2헤드, 2층) | **567.7** | 381.2 | 234.2 | 354.6 | 187.2 | 208.9 | 427.8 |
| small (B=32, T=64, d=128, 4헤드, 4층) | 86.6 | **87.4** | 65.2 | 31.1 | 31.1 | 43.5 | 41.3 |
| medium (B=32, T=128, d=256, 8헤드, 6층) | **13.70** | 12.39 | 12.80 | 5.77 | 6.69 | 7.00 | 5.39 |
| large (B=64, T=256, d=512, 8헤드, 8층)* | 0.94 | 0.87 | 0.97 | 0.47 | 0.51 | 0.51 | 0.28 |

\* large는 메모리를 많이 쓰므로 `--large`를 줘야 실행됩니다. 이 행은 이전 측정값으로, 이후의 GPU 스케줄 변경 뒤에는 다시 재지 않았습니다. 다만 large의 GPU 계획은 메모리 보호 규칙 때문에 그 측정 때와 같은 순서를 씁니다.

**읽는 법:**

- Apple GPU에서 `rg`는 MLX와 대체로 같은 수준이고 torch MPS와는 작은 모델에서 앞섭니다. 작은 차이는 순위로 읽지 마세요.
- CPU에서는 torch eager와 비슷합니다. 더 작은 차이는 측정 흔들림 안입니다.

## 메모리

| 설정 | rg 피크 라이브 | 재계산 없을 때 |
| --- | --- | --- |
| medium | 0.56 GB (CPU), 1.29 GB (GPU) | 1.20 GB |
| large | 5.01 GB | 12.66 GB |

같은 large에서 torch의 프로세스 최대 메모리는 7.46 GB였습니다. 위 수치는 중간 버퍼만 센 값이므로 직접 비교할 수 없습니다. `compiled.report["memory"]`에서 확인할 수 있습니다.

GPU는 작은 모델에서 메모리를 더 쓰고 배리어를 줄이는 순서를 고릅니다. 피크가 2 GB를 넘으면 메모리를 덜 쓰는 순서로 돌아갑니다.

중간 버퍼 계획이 물리 메모리의 절반을 넘으면 `compile`이 `PLAN_NEAR_PHYSICAL_MEMORY`로 경고합니다.

## 진단 비용

`validate="standard"`의 추가 비용은 컴파일 때 한 번만 듭니다. `run()`에는 계측 코드가 없습니다. 계측 실행(`compiled.check`)은 일반 호출의 약 2~5배이며, 실패 분석처럼 필요할 때만 씁니다.

## 측정으로 알게 된 것

프로파일러를 만든 이유입니다. 추측은 여러 번 틀렸습니다.

| 예상 | 실제 |
| --- | --- |
| 원소 연산이 병목이다 | MLP에서 역전파의 전치 복사가 시간의 47~62%였습니다. BLAS 전치 플래그로 없앴습니다 |
| CPU에서 Fusion이 빠르다 | 순차 Fusion은 중형에서 차이가 없고 대형에서 35% 느렸습니다. 스레드 비용을 회수할 만큼 큰 그룹만 만듭니다 |
| CPU의 큰 모델이 느린 이유는 Fusion 부재다 | 단일 스레드 축소·전치가 47%였습니다. 병렬화로 medium의 torch 대비 격차가 1.6배에서 1.1배로 줄었습니다 |
| 병렬화는 많을수록 좋다 | 합산에 임계값을 낮게 걸자 MLP 중형이 30% 느려졌습니다. 연산별 임계값이 필요합니다 |
| GPU면 빠르다 | 직접 쓴 행렬곱 셰이더로는 CPU보다 느렸습니다(medium 2.7). MPS로 바꾸고, 원소 연산을 더 합치고, 의존이 있을 때만 배리어를 넣어 MLX와 같은 수준이 됐습니다 |
| 큰 모델에서 MLX보다 1.3~1.5배 느리다 | 측정 착시였습니다. 일회성 버퍼 할당이 몇 스텝 안 되는 측정에 섞여 있었습니다. 제외하고 스텝을 늘리자 차이가 사라졌습니다 |
| CPU large가 느린 것은 커널 문제다 | 메모리 압박이었습니다. 중간값 12.66 GB로 스왑이 나서 시스템 시간이 사용자 시간의 두 배였습니다. GELU와 softmax의 중간값을 역전파 때 재계산해 5.01 GB로 줄이자 3배 빨라졌습니다 |
| 재계산은 언제나 이득이다 | 메모리가 충분한 MLP에서 `tanh` 재계산은 30% 느렸습니다. 비싼 함수는 피크가 2 GB를 넘을 때만 재계산합니다 |
| 드롭아웃이 학습을 늦춘다 | 드롭아웃은 거의 비용이 없었고 gradient 클리핑이 범인이었습니다. 전체 합산이 GPU 스레드 하나로 돌고 있었습니다. 행 단위로 나누자 50에서 84 steps/s가 됐습니다 |
| 배리어를 줄이면 무조건 좋다 | 레벨 순서로 배리어는 줄었지만 값이 오래 살아 large의 메모리가 5 GB에서 13 GB가 됐고, 측정 중 실제로 RAM 경고가 났습니다. 그래서 메모리 상한을 두었습니다 |
| CPU 폴백은 그 자체가 비싸다 | 비싼 것은 폴백 직전에 대기열을 비우는 일이었습니다. 키 분할 같은 작업을 스텝 맨 앞으로 옮겨 커맨드 버퍼를 스텝당 4개에서 2개로 줄였습니다 |

수식 재구성의 효과는 [컴파일러 연구 기록](compiler.md)에 있습니다.

## 남은 개선 여지

- 큰 모델의 GPU 순서: 메모리 상한 때문에 큰 모델은 배리어 절감을 못 받습니다. 메모리를 덜 늘리는 순서를 찾아야 합니다.
- `slice`, `pad`, `transpose`의 복사: 뷰로 바꾸면 메모리 트래픽을 줄일 수 있습니다.
- 네이티브 CPU 코드 생성: CPU의 원소 연산은 여전히 블록 인터프리터입니다.

프로파일은 다음처럼 볼 수 있습니다. GPU에서는 연산을 하나씩 실행해 GPU 타임스탬프로 재므로 연산 비율을 비교하는 데 쓰고, 실제 스텝의 비용은 `breakdown`(GPU 실행, 인코딩, 대기, CPU 폴백, 배리어 수)을 보세요.

```python
import rg

x = rg.zeros((128, 128))
c = rg.compile(lambda a: ((a @ a.T).tanh() * 2.0).sum(), (x,), validate="none")
report = c.profile(x, repeats=3)
assert report["microseconds_per_run"] > 0
```
